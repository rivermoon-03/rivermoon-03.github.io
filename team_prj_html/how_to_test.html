서버 자원 메트릭 시연 방식 비교 분석:
Mock Agent와 Docker 컨테이너

실제 GPU 클러스터 없이 서버 예약/할당 관리 시스템을 시연하기 위한 두 가지 접근에 대한 비교 보고서. 작동 원리, 기술 스택, 장단점, 구현 난이도, 유스케이스 적합도를 정리하여 팀 의사결정의 근거를 제공한다.

Executive Summary

두 방식 모두 시스템 동작 검증은 가능하다. Mock Agent 방식은 시나리오를 완벽히 통제할 수 있어 시연 흐름 설계에 유리한 반면 "실제로 동작하고 있다"는 발표 임팩트는 약하다. Docker 컨테이너 방식은 실제 부하를 보여줄 수 있어 임팩트가 크지만, 시간 통제와 환경 의존성이 부담으로 작용한다. 학기 일정과 발표 시간(약 20분)을 고려할 때, 두 방식을 결합한 하이브리드 접근이 가장 현실적이며 본 보고서가 권장하는 방향이다.

01Option A

Mock Agent

사전 정의된 클라이언트의 가상 메트릭 송출

구현 기간1–2주
실제 부하없음
통제 수준완전 통제

실제 부하를 발생시키지 않고, N개의 클라이언트 스크립트가 사전에 정의된 패턴(또는 시연자가 실시간으로 지정한 값)에 따라 가상의 CPU·메모리·네트워크 사용률을 백엔드로 송신한다. 별도의 Demo Conductor 컨트롤러가 각 에이전트의 행동을 시연 중 동적으로 변경한다.

1.1 작동 원리5단계

  1. Python 스크립트 mock_agent.py를 N개 인스턴스로 실행. 각 인스턴스는 고유한 서버 식별자(srv-01 등)를 보유.
  2. 각 에이전트는 1분 주기로 POST /metrics를 백엔드에 송신. 페이로드는 사인파+가우시안 노이즈로 합성된 사용률 값.
  3. Demo Conductor에서 슬라이더를 조작하면 POST /control이 해당 에이전트에 전달되며, 다음 송신 주기부터 값이 변경됨.
  4. UC14가 메트릭을 수신하면 UC15·UC18·UC19가 평소 로직대로 자동 반응. 시스템은 메트릭의 진위를 구분하지 못함.
  5. 송신 토글로 UC14 [E1] 응답 없음, 값 변조 옵션으로 [E2] 형식 오류 시나리오를 즉시 재현.

1.3 장단점 분석

Strengths
  • 완전한 시나리오 통제. "정확히 4% CPU를 31분간 유지" 같은 까다로운 조건도 가능.
  • 장비 의존성 없음. 노트북 1대로 충분.
  • 실패 분기(형식 오류·송신 단절·이상 징후)를 버튼 한 번에 재현.
  • 동일 입력 시 동일 출력. 시연 사고 위험이 낮음.
  • 구현 부담이 가볍다. Python 200~300줄 수준.
Weaknesses
  • 발표 임팩트가 제한적. "실제 동작" 인상이 약함.
  • 평가자의 "메트릭이 실제냐"는 질문에 대응이 어려움.
  • 실제 에이전트–서버 통신 프로토콜의 현실성 미검증.
  • OS 수준 실패(네트워크 단절 등)는 흉내내기 까다로움.

02Option B

Docker 컨테이너

실제 컨테이너에서 발생한 부하 메트릭 수집

구현 기간2–3주
실제 부하있음
통제 수준제한적

Docker 컨테이너 N개를 실제로 가동하고, 컨테이너 내부에서 stress-ng로 실제 CPU·메모리 부하를 발생시킨다. 백엔드는 docker stats / cgroup 인터페이스로 OS 커널이 측정한 진짜 사용률을 수집하여 사용한다.

Fig. 02Docker 컨테이너 토폴로지
REAL_LOADYes CONTROLdocker exec

2.1 작동 원리5단계

  1. 호스트 1대(노트북)에 Docker를 설치하고 docker-compose.yml로 4–6개 컨테이너 정의.
  2. 각 컨테이너에는 stress-ng가 사전 설치되어 있으며, 시연 중 docker exec srv-01 stress-ng --cpu 4로 실제 부하 발생.
  3. Metric Collector가 docker stats --no-stream을 5초 주기로 호출하여 cgroup이 측정한 실제 사용률 수신.
  4. Collector가 수신값을 POST /metrics로 백엔드에 전달. 이후 흐름은 Option A와 동일.
  5. UC15 시연 시 시연자는 srv-03을 idle 상태로 두거나 docker pause srv-03으로 CPU를 0%로 강제.

2.3 장단점 분석

Strengths
  • 발표 임팩트가 강함. "실제로 동작하고 있다"는 시각적 증거 확보.
  • OS 표준 메트릭 인터페이스 사용 → 실제 운영 환경과 유사한 데이터 경로.
  • 네트워크 단절·컨테이너 종료 등 현실적 장애 시연 가능(docker kill).
  • UC21 가용성(MTBF·MTTR) 그래프가 실제 의미를 가짐.
  • 산업 표준 도구 경험이 포트폴리오에 그대로 반영.
Weaknesses
  • 시간 통제 불가 — UC15의 "30분 유휴" 시연은 결국 스케줄러 가속에 의존.
  • 발표자 환경에 따라 결과가 변동. 부하 시 다른 컨테이너 영향 가능성.
  • Docker 설치 및 OS별 권한 차이로 환경 셋업에 시간 소요.
  • 형식 오류 등 미세 실패 분기는 재현이 까다로움.
  • 코드 및 운영 부담이 Option A의 1.5~2배.

Recommended Approach

제3안 · 하이브리드 구성

서버 4대 중 2대는 Docker 컨테이너 + stress-ng로 실제 부하, 나머지 2대는 Mock Agent로 시나리오 통제를 담당하는 절충 방식. 시연 시 발표자는 "이쪽은 실제 컨테이너에서 부하를 발생시키는 환경입니다"라고 안내한 후, 통제가 까다로운 시나리오(정확한 CPU 4% 유지·송신 형식 오류·30분 유휴)는 Mock 측에서 재현한다.

구현 부담은 Option B와 유사하나, Mock Agent가 독립적으로 동작하므로 시연 사고 발생 시 대체 가능하다는 안전성이 추가된다. 산업 도구 경험과 시연 안정성을 동시에 확보한다.

03.2Decision Guide

팀 내부 의사결정을 위한 판단 기준

팀원 구성, 일정 여유, 시연 목표에 따라 선택이 달라진다. 다음은 각 방식이 적합한 조건을 정리한 것이다.

A · Mock Agent 권장 조건
시연 안정성과 통제가 최우선일 때
팀 내 Docker 경험자가 부족하고, 발표 시연 안정성이 최우선이며, UC14~UC19의 자동화 분기를 정확히 시각화하는 것이 목표인 경우. 학기 일정이 빡빡한 상황에서 가장 안전한 선택지.
B · Docker 권장 조건
발표 임팩트와 학습 효과가 우선일 때
팀원 절반 이상이 Docker에 익숙하고, "실제 동작" 임팩트가 평가에 결정적이며, 산업 도구 경험을 이력에 남기고자 하는 경우. 구현 시간이 충분할 때 가장 매력적인 선택지.
Hybrid 권장 조건
양쪽 장점을 모두 확보하고 싶을 때
팀원 2–3명이 Docker 셋업을, 나머지가 Mock Agent를 병렬로 진행할 수 있는 경우. 일정 위험이 존재할 때 어느 한쪽이라도 시연 가능하다는 보험을 갖는 구성.
