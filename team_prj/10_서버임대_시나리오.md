# 10. 서버를 빌린다는 것 — 개념 및 전체 시나리오

> 이 문서는 "서버 예약/할당 관리 시스템"이 왜 필요한지, 그리고 사용자가 서버를 빌리는 과정이 실제로 어떻게 돌아가는지를 이야기 형식으로 설명합니다.

---

## 1. "서버를 빌린다"는 것이 무슨 뜻인가?

### 개념: 물리 자원의 시간 공유

서버는 CPU·RAM·스토리지가 달린 물리 컴퓨터입니다. 서버를 "소유"하지 않고 "빌린다"는 말은, **그 컴퓨터의 시간을 나눠 쓴다**는 뜻입니다.

```
[호텔 방 비유]

소유       = 집을 산다     → 서버 1대를 연구실 혼자 전용으로 구입
임대(빌림) = 호텔에 묵는다 → 내가 필요한 기간만 서버의 자원을 할당받아 사용

호텔방이 비어 있으면 다음 손님이 쓸 수 있듯,
서버도 내가 반납하면 즉시 다른 팀원이 사용할 수 있습니다.
```

### 연구실 맥락: 내부 클라우드

대형 클라우드(AWS/GCP)는 인터넷 너머 데이터센터를 빌려주고 과금합니다. 이 시스템은 그 원리를 **연구실 내부 서버 풀**에 적용한 것입니다.

```
┌─────────────────────────────────┐
│         연구실 서버 풀           │
│  [svr-01]  [svr-02]  [svr-03]  │
│   GPU×4     GPU×2     CPU×32   │
└────────────┬────────────────────┘
             │ 예약/할당 시스템이 중재
   ┌──────┬──┴───┬──────┐
  STU-1  STU-2  MGR  ADM
```

서버는 변하지 않지만 **누가, 언제, 얼마나** 쓸 수 있는지를 시스템이 관리합니다.

## 2. 전체 흐름 한 눈에 보기

```
[내가 원하는 것]      [시스템이 하는 일]          [결과]
  
서버 고르기    →  현황 조회 (UC01)           → 가용 서버 목록 확인
기간 정하기    →  예약 요청 (UC04/UC05)      → Quota 확인·낙관적 잠금
              →  (초과 시) 승인 요청 (UC08)  → MGR 결재 대기
쓰기          →  서버 IN_USE 상태 유지        → 작업 수행
반납          →  반납 (UC07)                 → 서버 AVAILABLE 복귀
```

## 3. 시나리오 A — 정상 예약 (Quota 여유 있음)

> **등장인물:** 강다은(STU) — 딥러닝 모델 학습을 위해 GPU 서버가 필요한 석사 과정생

### 3-1. 서버 현황 확인

강다은은 로그인 후 **서버 현황 화면(UC01)**을 엽니다.

```
[화면]
┌──────────┬────────────┬──────────┬──────────────────┐
│ 서버명   │ 사양       │ 상태     │ 가용 기간        │
├──────────┼────────────┼──────────┼──────────────────┤
│ svr-01   │ GPU×4 32GB │ AVAILABLE│ 즉시 ~ 무한대    │
│ svr-02   │ GPU×2 16GB │ RESERVED │ 5월 17일 이후    │  ← 다른 팀원이 예약 중
│ svr-03   │ CPU×32 64GB│ IN_USE   │ 사용 중          │  ← 사용 불가
└──────────┴────────────┴──────────┴──────────────────┘
```

- `AVAILABLE` = 지금 당장 빌릴 수 있음
- `RESERVED`  = 누군가 기간을 잡아둠 (내 기간과 겹치지 않으면 예약 가능)
- `IN_USE`    = 현재 사용 중 (반납될 때까지 대기)
- `MAINTENANCE` = 점검 중

### 3-2. 예약 요청

강다은이 svr-01 을 선택하고 기간을 입력합니다.

```
[예약 폼]
서버  : svr-01 (GPU×4 32GB)
시작  : 2026-05-14 09:00
종료  : 2026-05-21 18:00
기간  : 7일 → Quota 7 소모 예정

                    [예약 요청]
```

### 3-3. 시스템이 내부적으로 하는 일

```
① Quota 잔여 확인
   강다은의 남은 Quota: 10 / 팀 한도: 30
   요청량: 7  →  10 ≥ 7 ✓

② 낙관적 잠금(동시 예약 충돌 방지)
   SELECT svr-01 WHERE status='AVAILABLE' AND version=42
   →  조건 만족, version을 43으로 +1

③ 트랜잭션 (한 묶음으로 처리)
   - Server.status = RESERVED
   - Reservation 레코드 생성
   - Quota.used += 7
   - 모두 성공해야 커밋, 하나라도 실패하면 전부 롤백
```

### 3-4. 결과

```
✅ 예약 확정!

서버: svr-01 | 기간: 5/14 09:00 ~ 5/21 18:00
남은 Quota: 3 (10 - 7)

[내 예약 보기]  [서버 접속 정보]
```

강다은은 예약 기간 동안 svr-01에 SSH로 접속해 모델을 학습시킵니다.

### 3-5. 반납

학습이 끝나면 **반납(UC07)**합니다.

```
강다은: [반납하기] 클릭
시스템:
  - Server.status = AVAILABLE  ← 즉시 다음 사람이 예약 가능
  - Quota.used -= 7             ← 강다은 Quota 7 회복
  - Reservation.status = RETURNED
```

## 4. 시나리오 B — Quota 초과 → 승인 요청

> **상황:** 강다은의 남은 Quota가 3인데, 10일 예약을 시도

### 4-1. 시스템이 막음

```
❌ Quota 부족
남은 Quota: 3 / 요청: 10
초과량: 7

"팀 관리자에게 초과 승인을 요청하시겠습니까?"
  [승인 요청]   [취소]
```

### 4-2. 승인 요청(UC08) 발송

강다은이 [승인 요청]을 누르면:

```
시스템: ApprovalRequest 생성
→ MGR(지도교수/팀장)에게 알림 발송

[MGR 화면]
"강다은이 svr-01 / 10일 / 초과 7 Quota 승인을 요청했습니다."
  [승인]  [기간 단축 후 승인]  [거절]
```

### 4-3. 두 가지 결과

| MGR 액션 | 시스템 처리 | 강다은 알림 |
|----------|------------|------------|
| 승인 | 예약 자동 확정 | "승인되었습니다 — svr-01 10일 예약 확정" |
| 거절 | 예약 생성 안 됨 | "거절되었습니다 — 사유: [MGR 입력 내용]" |
| 무응답 72h | 자동 거절(UC17) | "72시간 무응답으로 자동 거절되었습니다" |

## 5. 시나리오 C — 동시 충돌 (다른 사람이 0.1초 먼저 잡음)

> **상황:** 강다은과 이준혁이 같은 svr-01을 거의 동시에 예약 시도

```
강다은  ──────── SELECT version=42 ─────── UPDATE (version=42) ─── ✅ 성공
                                                                 (version → 43)
이준혁  ─── SELECT version=42 ──────────────── UPDATE (version=42) ─── ❌ 실패
                                                                   (이미 version=43)
```

이준혁 화면:

```
⚠️ 다른 사용자가 방금 예약했습니다.

지금 예약 가능한 대안 서버:
  • svr-04  GPU×2  AVAILABLE  →  [바로 예약]
  • svr-05  CPU×16 AVAILABLE  →  [바로 예약]
```

충돌이 발생해도 **데이터는 절대 꼬이지 않습니다.** 낙관적 잠금이 이를 보장합니다.

## 6. Quota가 왜 필요한가?

서버는 공유 자원입니다. Quota가 없으면 한 사람이 서버 전체를 독점할 수 있습니다.

```
[Quota 계층 구조]

ADM이 팀 전체 한도 설정
  └─ 팀 Quota: 30 (동시 30일치 예약 가능)
       ├─ 강다은:   10
       ├─ 이준혁:   10
       └─ 박서연:   10

강다은이 7일 예약하면: 강다은 잔여 3, 팀 잔여 23
강다은이 초과하려면: MGR 승인 필요 (팀 Quota 범위 내에서만 가능)
MGR이 팀 한도를 초과하려면: ADM 승인 필요
```

---

## 7. 자동화가 하는 일

사람이 직접 하지 않아도 시스템이 스스로 처리하는 것들:

| 상황 | 시스템 자동 처리 | 관련 UC |
|------|----------------|---------|
| 예약 종료 시각 도래 | 서버 자동 반납 + Quota 회복 | UC16 |
| 서버 미사용(5% 이하 30분) | 경고 알림 → 15분 후 자동 회수 | UC15 |
| MGR 무응답 72시간 | 승인 요청 자동 거절 | UC17 |
| 사용률 1분마다 수집 | 유휴 감지 데이터 축적 | UC14 |

## 8. 전체 상태 전이도

```
서버 상태:
  AVAILABLE ──[예약]──→ RESERVED ──[사용 시작]──→ IN_USE
      ↑                    │                         │
      └──[반납/취소/만료]──┘◄───────[반납/회수/만료]─┘
      
      ←──────[ADM 점검 등록]──→ MAINTENANCE ──[점검 완료]──→

예약 상태:
  RESERVED → IN_USE → RETURNED
                    → EXPIRED  (기간 만료 자동 반납)
                    → RECLAIMED (유휴 회수)
           → CANCELED (사용자 취소)
```

---

> **핵심 한 줄 요약:** 서버를 빌린다 = 필요한 기간만 컴퓨팅 자원을 점유하고, 쓰고 나면 다음 사람이 쓸 수 있도록 돌려주는 것. 이 시스템은 그 과정에서 생기는 충돌·독점·방치를 자동으로 해결합니다.
