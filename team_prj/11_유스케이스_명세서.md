# 서버 예약/할당 관리 시스템 — 유스케이스 명세서

> v1.0  ·  UC 20건  ·  그룹 6개

---

## 용어 설명

| 용어 | 설명 |
|------|------|
| **Quota** | 팀 또는 개인이 동시에 점유할 수 있는 서버 사용 한도(일 수 기준). 서버를 반납하면 사용한 만큼 자동으로 회복된다. |
| **서버 상태** | `AVAILABLE` 지금 바로 예약 가능 / `RESERVED` 기간이 선점된 상태 / `IN_USE` 현재 사용 중 / `MAINTENANCE` 점검 중 |
| **낙관적 잠금** | 두 사람이 같은 서버를 동시에 예약하려 할 때 충돌을 막는 기법. 서버마다 `version` 번호를 두고, 저장 직전에 번호가 바뀌어 있으면 뒤늦은 요청을 자동으로 취소하고 안내한다. |
| **ApprovalRequest** | Quota 한도를 초과해 예약하려 할 때 자동으로 생성되는 관리자 결재 건. 상태: `PENDING(대기)` → `APPROVED(승인)` / `REJECTED(거절)` / `AUTO_REJECTED(72시간 무응답 자동 거절)` |
| **Reservation** | 서버 예약 한 건의 기록. 사용자·서버·기간·상태 정보를 담는다. |
| **Notification** | 시스템이 사용자에게 보내는 내부 알림 기록. 사용자가 읽으면 확인 시각(readAt)이 기록된다. |

## 유스케이스 수준

| 수준 | 설명 |
|------|------|
| **요약** | 여러 사용자 목표를 묶는 상위 시나리오. 한 번의 인터랙션으로 끝나지 않는다. |
| **사용자 목표** | 사용자가 한 세션에서 달성하려는 목표. 대부분의 UC가 여기에 해당한다. |
| **하위 기능** | 다른 UC 내부에서 호출되거나 시스템이 자동으로 실행하는 세부 단계. 단독으로는 사용자 가치를 완성하지 못한다. |

## 액터

| 코드 | 이름 | 역할 |
|------|------|------|
| `STU` | 학생 / 연구원 | 시스템 주 사용자. 소속 팀 Quota 내에서 서버를 요청·사용·반납한다. |
| `MGR` | 팀 관리자 / 교수 | 팀 단위 운영. 팀원의 Quota 초과 요청을 결재하고 팀원별 Quota를 조정한다. |
| `ADM` | 서버 관리자 | 시스템 최고 권한자. 서버 자원과 전체 정책을 관리한다. |
| `SYS` | 모니터링 시스템 | 사람 개입 없이 정해진 일정이나 조건에 따라 자동으로 동작하는 시스템. |

## 부록 A — 구현 메모

> 본 부록은 본문(유스케이스 명세) 수준에서는 추상화된 구현 디테일을 모아둔 참고용 섹션이다. SQL 조건식·엔티티 필드·enum 값·시각 비교식 등 구현 시 필요한 구체성을 보존한다.
> 각 절에는 **요약 항목** 다음에 *"설명 :"* 단락을 두어, 문서를 처음 읽는 사람도 의미를 파악할 수 있도록 했다.

### A.0 들어가기 전에 — 자주 등장하는 개념

부록을 읽기 전에 알아두면 좋은 용어를 정리한다.

| 용어 | 한 줄 설명 |
|---|---|
| **DB / 데이터베이스** | 사용자·서버·예약 같은 정보를 표(테이블) 형태로 저장해두는 저장소. |
| **엔티티 (Entity)** | DB 테이블 한 줄로 표현되는 객체. 예: `Reservation`(예약 한 건), `Notification`(알림 한 건). |
| **필드 (Field)** | 엔티티가 가진 속성 하나. 예: `Reservation`의 `userId`, `startTime`, `endTime`. |
| **enum** | 미리 정해둔 값 목록. 예: `Reservation.status`는 `RESERVED`/`IN_USE`/`RETURNED`/`EXPIRED`/`RECLAIMED`/`CANCELED` 중 하나만 가질 수 있다. |
| **트랜잭션 (Transaction)** | 여러 DB 변경을 "전부 성공" 또는 "전부 취소"로 묶는 단위. 중간에 한 단계라도 실패하면 모든 변경이 되돌려진다. |
| **낙관적 잠금 (Optimistic Lock)** | "내가 처음 본 그대로 아무도 바꾸지 않았겠지"라고 가정하고 진행하다가, 저장 직전에 누가 먼저 바꿨는지 `version` 번호로 확인하는 방식. 패배한 트랜잭션은 자동 롤백된다. |
| **SQL `WHERE` 조건** | "이 조건에 맞는 행만 골라라"라는 DB 명령. `?`는 코드에서 채워 넣는 값 자리. |
| **`SELECT FOR UPDATE`** | 행을 골라내면서 "이 행은 내 트랜잭션이 끝날 때까지 다른 사람이 손대지 못한다"라고 잠그는 명령. 동시 결재 같은 경합에서 한 명만 성공하게 만든다. |
| **soft delete** | 데이터를 실제로 삭제하지 않고 `deletedAt` 시각만 기록해 "지운 것으로 취급"하는 방식. 감사·복구에 유리하다. |
| **시계열 저장소** | 시간 순서대로 측정값(사용률 등)을 누적 저장하는 전용 DB. |
| **멱등성 (Idempotency)** | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 똑같이 유지되는 성질. 네트워크 재시도로 인한 중복 처리를 막는다. |

### A.1 UC04 — 예약 요청 SQL

- 낙관적 잠금 UPDATE 조건: `WHERE id=? AND version=?`. 영향 행이 0이면 충돌로 판정한다.
- 멱등성 키 재수신 시 이전 결과를 그대로 반환하여 중복 예약을 방지한다.

> **설명 :** 예약 화면을 연 시점의 `version`(예: 42)을 기억해뒀다가, 저장할 때 "ID도 같고 version도 42인 행"을 찾는다. 누군가 0.1초 먼저 예약해서 version이 43으로 바뀌어 있으면 검색 결과가 0건이 되어 내 요청은 실패한다. 이게 충돌 감지의 핵심이다.
> "멱등성 키"는 클라이언트가 요청마다 붙이는 고유 ID로, 네트워크 끊김 때문에 같은 요청을 두 번 보내도 서버가 "이 키는 이미 처리됐다"라고 알아채고 똑같은 결과만 돌려준다 — 예약이 두 번 잡히는 사고를 막는다.

### A.2 UC08 — ApprovalRequest 필드

- 생성 시 채우는 필드: `requesterId, approverId(=팀의 MGR), requestedAt = now, reason, status = PENDING`.

> **설명 :** 학생이 "Quota 초과 승인 요청"을 누르는 순간 DB에 결재 카드 한 장이 만들어진다. 그 카드의 각 칸이 위 필드다 — *누가 요청했는지(requesterId)*, *누가 결재해야 하는지(approverId, 보통 그 팀의 MGR)*, *언제 요청했는지(requestedAt)*, *왜 필요한지(reason)*, *현재 상태(status — 처음엔 항상 PENDING="대기 중")*.

### A.3 UC09 / UC17 — 결재 동시성

- 결재(UC09)와 타임아웃(UC17)의 경합은 `SELECT FOR UPDATE` 또는 `status = 'PENDING'` 가드 조건으로 1건만 성공하도록 제어한다.

> **설명 :** 72시간이 거의 다 됐을 때 두 가지 일이 동시에 벌어질 수 있다 — MGR이 막 "승인" 버튼을 누르고, 시스템이 동시에 "타임아웃이니 자동 거절"을 처리한다. 그대로 두면 같은 결재 건이 두 번 처리될 수 있다.
> 이를 막는 방법은 두 가지: (1) `SELECT FOR UPDATE`로 결재 카드를 잠가서 한 트랜잭션이 끝날 때까지 다른 트랜잭션을 기다리게 하거나, (2) UPDATE 시 `WHERE status = 'PENDING'` 조건을 붙여서 "아직 처리 안 된 카드만 바꿔라"라고 못 박는다. 어느 쪽이든 둘 중 한 명만 성공한다.

### A.4 UC09 — 결재 기록 필드

- 상태 전이 시 함께 기록: `decidedAt = now`, `decidedBy`.

> **설명 :** 결재 카드의 상태가 PENDING → APPROVED(또는 REJECTED)로 바뀔 때, "언제(`decidedAt`)·누가(`decidedBy`) 결정했는지"를 함께 적어둔다. 나중에 "이 거절은 언제 누가 한 거야?"라는 질문에 답할 수 있게 하기 위한 흔적(감사 자료)이다.

### A.5 UC03-* — Notification 필드

- type enum: `APPROVAL_RESULT`, `IDLE_RECLAIM_WARNING`, `RESERVATION_CONFLICT`, `RESERVATION_EXPIRY_PRE`, `RESERVATION_EXPIRY_DONE`.
- 공통 필드: `userId, type, message, payload, sentAt, readAt`.
- UC03-d의 payload는 대안 서버 목록을 담는다.
- 사용자가 알림을 읽으면 `readAt`이 기록된다.

> **설명 :** 시스템이 보내는 모든 알림은 같은 모양("Notification 엔티티")으로 저장되고, *어떤 종류의 알림인지(`type`)*만 다르다.
> - `APPROVAL_RESULT` — 승인/거절 결과
> - `IDLE_RECLAIM_WARNING` — "서버가 놀고 있으니 곧 회수합니다" 경고
> - `RESERVATION_CONFLICT` — "방금 다른 사람이 먼저 잡았어요" 충돌 알림
> - `RESERVATION_EXPIRY_PRE` / `_DONE` — 만료 1시간 전 예고 / 만료 완료
>
> `message`는 사람이 읽는 문장이고, `payload`는 함께 딸려 가는 부가 데이터다. 예약 충돌 알림은 payload에 "대신 쓸 수 있는 다른 서버 목록"을 담아 같이 보낸다.
> `sentAt`은 보낸 시각, `readAt`은 사용자가 알림함에서 그 알림을 열어본 시각이다. `readAt`이 비어 있으면 "안 읽음 배지"가 표시된다.

### A.6 UC15 — 회수 예정 시각 및 트랜잭션

- 회수 예정 시각 = 알림 발송 시각 + `IDLE_WARNING_GRACE` (예시: 15분).
- 회수 트랜잭션: `Reservation.status = RECLAIMED`, `Server.status = AVAILABLE`, `Server.version += 1`, `Quota.used -= 점유량`.

> **설명 :** 서버가 30분간 거의 안 쓰이고 있으면 시스템이 즉시 뺏는 게 아니라, 먼저 "15분 후에 회수합니다" 경고를 보낸다. 사용자가 그 사이 "쓰고 있어요" 버튼을 누르면 회수가 취소된다.
> 15분이 지나도 여전히 유휴라면 회수가 진행되는데, 이때 4가지 변경을 **한 묶음(트랜잭션)**으로 처리한다:
> 1. 예약 카드 상태 → `RECLAIMED`(회수됨)
> 2. 서버 상태 → `AVAILABLE`(다음 사람이 쓸 수 있음)
> 3. 서버의 `version` +1 (낙관적 잠금용 번호 갱신)
> 4. 사용자 Quota.used 감소 (썼던 만큼 한도가 회복됨)
>
> 4가지 중 하나라도 실패하면 전부 원상복구된다 — "예약은 회수됐는데 Quota는 안 돌려받는" 같은 어긋난 상태가 절대 생기지 않는다.

### A.7 UC16 — 만료 조건식

- 사전 알림 대상: `endTime - EXPIRY_PRENOTIFY_LEAD ≤ now < endTime`.
- 만료 처리 대상: `endTime ≤ now`.
- 시각 비교는 항상 DB 서버 시각을 기준으로 한다.

> **설명 :** 시스템이 1분마다 모든 예약을 훑으며 두 가지 부등식을 확인한다.
> - 첫 번째 식 — "지금 시각이 *종료 1시간 전*과 *종료 시각* 사이인가?" → 맞으면 "1시간 후 만료" 사전 알림을 보낸다.
> - 두 번째 식 — "종료 시각이 이미 지났는가?" → 맞으면 자동 반납을 실행한다.
>
> "DB 서버 시각 기준"이라는 단서는, 시스템이 여러 컴퓨터에 나뉘어 돌아갈 때 각 컴퓨터의 시계가 조금씩 어긋날 수 있기 때문이다. 어느 시계를 믿을지 미리 정해두지 않으면 만료 판정이 들쭉날쭉해진다.

### A.8 UC17 — 타임아웃 조건식

- 대상 조회: `now - requestedAt ≥ APPROVAL_TIMEOUT AND status = 'PENDING'`.
- 전이 시 함께 기록: `status = AUTO_REJECTED, decidedAt = now, decidedBy = 'SYSTEM'`.

> **설명 :** 시스템이 주기적으로 결재함을 훑으면서 "요청한 지 72시간(`APPROVAL_TIMEOUT`)이 넘었고, 아직 *대기 중(PENDING)*인 결재"를 찾는다. 그런 결재가 있으면 상태를 `AUTO_REJECTED`("시스템이 자동 거절")로 바꾸고, *언제(`decidedAt`)*와 *누가(`decidedBy = 'SYSTEM'` — 사람이 아닌 시스템)*를 기록한다.
> 이 흔적 덕분에 나중에 "이 거절은 MGR이 한 거야, 시스템이 한 거야?"를 구분할 수 있다.

### A.9 UC01 / UC12 — 감사 로그

- UC01: 조회 이벤트 로그를 ADM·MGR 권한 한정으로 1건 기록한다.
- UC12: soft delete(`deletedAt = now`) 시 감사 로그 1건을 기록한다. 삭제 후에도 UC14가 수집한 과거 메트릭은 보존된다.

> **설명 :** "감사 로그(audit log)"는 "누가·언제·무엇을 했는지"를 따로 기록해두는 흔적이다. 학생이 서버 현황을 보는 것까지 다 기록하면 양이 너무 많아지므로, 관리자급(ADM·MGR)이 조회할 때만 기록한다.
> 서버 삭제는 영구 삭제가 아니라 *soft delete*다 — 데이터를 실제로 지우지 않고 `deletedAt`에 "지운 시각"만 적어둔다. 그래서 삭제된 서버라도 과거 사용률 데이터는 그대로 남아 있어, 나중에 "그 서버 마지막 한 달 사용량은 어땠지?" 같은 조회가 가능하다.

### A.10 UC13 — MaintenanceSchedule

- 점검 일정은 `MaintenanceSchedule` 엔티티로 저장한다.
- SYS 스케줄러가 `startTime` 도래 시 Server.status를 `MAINTENANCE`로, `endTime` 도래 시 `AVAILABLE`로 자동 전이한다 (낙관적 잠금 적용).

> **설명 :** ADM이 "이번 주 일요일 02:00~04:00에 svr-01 점검"을 등록하면, 그 정보가 `MaintenanceSchedule`이라는 별도 테이블에 한 줄로 저장된다. ADM이 02:00에 직접 버튼을 누르는 게 아니라, 시스템 스케줄러가 그 시각이 되면 알아서 서버 상태를 `MAINTENANCE`로 바꾸고, 04:00이 되면 `AVAILABLE`로 되돌린다.
> "낙관적 잠금 적용"이라는 단서는, 그 순간 다른 사람이 서버에 뭔가를 하고 있을 수도 있으므로 `version` 비교로 충돌을 감지한다는 뜻이다.

### A.11 UC14 — 시계열 저장소 장애 대응

- 저장 실패 시 메모리 버퍼에 임시 보관 → 복구되면 재기록.
- 버퍼 한도 초과 시 가장 오래된 데이터부터 폐기하고 ADM에게 경고를 발송한다.
- 에이전트 시각과 시스템 시각의 차이가 허용 범위를 초과하면 시스템 시각으로 통일하여 기록한다.

> **설명 :** 사용률(CPU/메모리 등)은 시계열 저장소라는 전용 DB에 1분마다 쌓인다. 그런데 이 저장소가 잠시 고장 나면? 측정값을 그냥 버리는 게 아니라 **시스템 메모리에 임시로 쌓아둔다**. 저장소가 복구되면 쌓인 값들을 한꺼번에 다시 기록한다.
> 메모리에도 한도가 있어서 너무 오래 고장 나면 결국 일부를 버려야 하는데, 그때는 "오래된 것부터" 버리고 ADM에게 "데이터가 유실되고 있다"라고 경고를 보낸다.
> 마지막 항목 — 각 서버의 에이전트가 보내는 시각이 시스템 시각과 다를 수 있다(시계가 어긋난 상태). 격차가 너무 크면 그 값을 그대로 믿지 않고, 시스템 자신의 시각으로 덮어써서 기록의 일관성을 지킨다.
